In the JVM, every Java object contains an object header that stores metadata, such as lock information, hash codes, GC status, and a pointer to its class. These data are essential for the JVM’s internal operations but do not contain any application-specific information. As a result, they are generally considered memory overhead required to run the JVM.

Currently in a 64-bit JVM, the default size of an object header is 12 bytes, consisting of an 8-byte mark word and a 4-byte compressed class pointer. According to the Lilliput experiment result [1], the average size of a Java object ranges from 32 to 64 bytes, with the object header accounting for 37.5% to 18.75% of that size. This significant overhead has long been a source of criticism for the JVM, leading to the introduction of an OpenJDK project known as Project Lilliput.

The core idea of Project Lilliput is relatively straightforward: reducing the size of the object header. To illustrate this, let’s assume that the average size of a Java object is 32 bytes. If the original 12-byte object header is reduced to 8 bytes, it would result in a 12.5% memory saving. If the header size is further reduced to 4 bytes, the memory saving would reach 25%. According to JEP 450 [2], real-world applications have shown that reducing the size of the object header can achieve memory savings of 10% to 20%.

# Layout of the mark word

So how does Project Lilliput achieve object header compression? To answer this question, we first need to understand the layout and purpose of the mark word. In a 64-bit JVM, prior to JDK 24, the structure of the mark word was as follows:

```
-------- -------- -------- -HHHHHHH HHHHHHHH HHHHHHHH HHHHHHHH -AAAALLL
```

Each letter here represents a bit. Let’s break it down: the first 25 bits are unused; the next 31 bits store the identity hash code. It’s important to note that this identity hash code may be different from the hash value returned by the hashCode method, which can be overridden in Java classes. When System.identityHashCode or the default native implementation of Object.hashCode is called for the first time, the JVM calculates a 31-bit integer based on the object’s memory address and caches it in this region. From that point onward, all subsequent calls to these methods will return the cached value. This mechanism ensures that a Java object consistently returns the same identity hash code throughout its lifecycle.

Following the 31 bits allocated to the hash code, there is 1 unused bit. The next 4 bits are used to store the GC age of the Java object. This value indicates the number of YGC the object has survived. Once this value reaches a certain threshold, the JVM promotes the object to the old generation.

The final three bits of the mark word represent the lock state of the object. Here's how they are used: The third-to-last bit indicates whether the object is biased-locked, but this feature was removed starting from JDK 18 [3]. The two least significant bits have four possible combinations representing different lock states:

* 00: The object is locked using a thin lock.
* 01: The object is unlocked (default state).
* 10: The object uses a heavy monitor but is not necessary locked.
* 11: Marked by GC to indicate the object was relocated.

In all cases except for the unlocked state (01), the upper bits of the mark word contain a pointer to relevant information:

```
PPPPPPPP PPPPPPPP PPPPPPPP PPPPPPPP PPPPPPPP PPPPPPPP PPPPPPPP PPPPPLLL
```

The meaning of the pointer varies depending on the lock state:

Thin lock (LL = 00):The pointer references a lock slot in the Java thread's stack frame. Hence, thin locks are also referred to as stack locks.
Heavy monitor (LL = 10): The pointer references a heavy monitor in the JVM.
GC mark (LL = 11):The pointer references the object’s new memory location in the Java heap after the object has been relocated by the garbage collector.
Prior to JDK 18, in the case of biased locking (LLL = 100), the pointer referenced the thread that owned the lock.

There are two key points to note here:

1. Object alignment. Since the three least significant bits are used to store lock state, the pointer must be aligned to an 8-byte boundary. Such alignment ensures that the pointer's three least significant bits are always zero, making room for lock state bits. This requirement also matches the fact that Java objects in the JVM are aligned to 8-byte boundaries, which can be configured via -XX:ObjectAlignmentInBytes=8, with valid values ranging from 8 to 256 bytes.
2. Displaced mark word. When the upper bits of the mark word store a non-zero value, such as a cached identity hash code, overwriting it with a pointer would result in data loss. For instance, if the object's address changes, recalculating the hash code would yield a different value. To avoid this, the JVM copies the original mark word to the memory location referenced by the pointer, known as the displaced mark word. Whenever the JVM needs to read or write the original mark word, it must access the displaced mark word through the pointer.

As we can see, there are 25+1+1 biased locking bit, totaling 27 unused bits. The core idea of Project Lilliput is to embed the class pointer into the mark word, reducing the size of the object header from 12 bytes to 8 bytes. However, this approach faces two major challenges:

1.Not enough unused bits to host a full 32-bit compressed class pointer. There are two solutions to this:
    a. Compressing the identity hash code. A hash code is essentially a random number. In theory, even returning 0 every time would technically fulfill the definition of a hash code. However, the quality of the hash code directly impacts the efficiency of many algorithms. For example, HashMap relies on hash codes (not necessarily identity hash codes) to distribute objects across different buckets, which then improves lookup efficiency. A well-distributed hash code minimizes collisions, leading to faster lookups. Therefore, compressing the hash code could potentially impact the performance of real-world applications
    b. Further compressing the class pointer. The current compressed class pointer technique can be viewed as reducing the 64-bit reference to a 32-bit array index, which points to an entry in a class array in the class metaspace. Further compression would involve reducing the range of the index values. For example, if we use only the first 25 bits, the JVM would still be able to support up to 2²⁵ = 33,554,432 unique Java classes, which is typically more than sufficient for most applications. Additionally, not all Java classes need to be stored in the class array. Since Java objects are always instances of a concrete class, abstract classes and interfaces, which have no direct instances, do not need to be referenced by any Java object and thus can be excluded from that class array. Starting with JDK 24, this optimization has already been introduced, moving abstract classes and interfaces out of the class metaspace into a separate storage area [4].
2. Changes to retrieving the class of an object. By embedding the class pointer into the mark word, the process of retrieving a Java object’s class needs to be adjusted. When the JVM needs to access the object's class, it must first check whether the object is using a displaced mark word. If the displaced mark word is used, the JVM needs to dereference the pointer and extract the compressed class pointer from the displaced mark word. However, getClass is a rather frequent operation in the JVM. Even if only a small percentage of objects are locked, this additional check introduces overhead that could impact performance. A worse problem happens when a concurrent GC attempts to fetch the mark word while it is being displaced. To handle such potential races, extra care must be taken in the concurrent GCs.
The designers of Lilliput prefer to avoid the displaced mark words. This requires a redesign of the thin locking and heavy monitor locking mechanisms within the JVM, to enable quick access of the corresponding lock structures without needing to rely on the mark word pointer.

# Replacement of the Stack Locking: Lightweight Locking

Lightweight locking (enabled via -XX:LockingMode=2) is not an entirely new feature introduced in JDK 24. In fact, it was first introduced during the JDK 21 development cycle and was even set as the default locking mechanism at one point [5]. However, prior to the official release of JDK 21, the feature was reverted to non-default status due to stability concerns. In subsequent JDK versions, the lightweight locking became the default option again and has continued to be optimized, such as the introduction of recursive lock support [6].

Lightweight locking shares a similar design philosophy with the legacy stack locking, both being based on the assumption of low lock contention — that is, most locks are expected to have no competing threads. When lock contention occurs, the JVM will inflate the lock into a heavy monitor to handle the situation. Therefore, lightweight locking does not need to implement the complex mechanisms of heavy monitor, such as wait queue management. 

The primary task of both stack locking and lightweight locking is to establish a mapping between a Java object and the thread holding the lock to determine whether the current thread owns the lock. Stack locking achieves this by storing a pointer in the mark word that references the lock slot in the Java stack frame of the thread holding the lock. Since the memory space of each thread is known to the JVM, it can quickly identify which thread holds the lock by following this pointer.

In contrast, lightweight locking uses a different approach. The JVM maintains a lock stack in thread-local memory, which records all the Java objects currently locked by that thread. When a thread acquires a lock, the corresponding Java object is pushed onto the lock stack. When the lock is released, the object is popped from the stack. The process for determining the lock owner is as follows:

* If the lock stack contains the Java object, it indicates that the current thread holds the lock.
* If the lock stack does not contain the Java object, it means that another thread holds the lock. In this case, the JVM inflates the lightweight lock into a heavy monitor to handle the contention.

Specifically, the JVM maintains the following data structure in thread-local memory to manage the state of lightweight locking:

```
class LockStack {
  uint32_t _top;
  const uintptr_t _bad_oop_sentinel = -1;
  oop _base[8];
}
```

Here, _bad_oop_sentinel is used to detect out-of-bound unlock operations. _top acts as an index into the Java object reference array _base, and always points to the current empty position at the top of the stack. Based on this data structure, the locking and unlocking operations can be described using the following pseudo-code:

```
def lightweight_lock(obj):
  if 0<= _top < 8 and CAS(obj._mark, LOCKED):
    _base[_top++] = obj
  else: inflate to heavy monitor

def lightweight_unlock(obj):
  _top--
  CAS(obj._mark, UNLOCKED)
```

Here, CAS refers to the compare-and-swap atomic operation, which returns true if the swap is successful.

Consider the following recursive locking scenario:

```
synchronized (obj) {    // monitor_enter obj
  synchronized (obj) {  // monitor_enter obj
    ...
  }                     // monitor_exit obj
}                       // monitor_exit obj
```

In the second line, the JVM encounters a recursive lock on the same object. With stack locking, the JVM could quickly determine whether the current thread holds the lock by checking the pointer in the object header. If the thread already owns the lock, the JVM marks it as a recursive lock in the lock slot and "skips" the unlock operation in the fourth line. This prevents the object from being mistakenly set to an unlocked state.

With lightweight locking, however, the process of identifying recursive locks is more complex:

* Locking: When a thread encounters an already-locked object, the JVM must scan the entire lock stack to check if the current thread already holds the lock. This scan is necessary to determine whether the lock is recursive. Though, since lightweight locking are designed under the assumption of low contention, encountering an already-locked object is rare. Recursive locks can also be avoided with careful code practices, so the additional lock stack scan is rare and generally acceptable.
* Unlocking: When unlocking, the JVM must perform a full lock stack scan to determine whether the lock is recursive. This step is mandatory for all unlock operations, meaning that every unlock requires scanning the entire lock stack to avoid accidentally unlocking a recursive lock. This unconditional lock stack scan during unlock can have a significant performance impact on Java applications, especially in cases where locks are frequently acquired and released.

Lightweight locking adopts a compromise for handling recursive locks — it only checks the top element of the lock stack. When encountering an already-locked Java object, the JVM compares it with the stack's top object:

If they match, the JVM treats it as a recursive lock.
If they don’t match, the JVM inflates the lightweight lock to a heavy monitor, regardless it might be a recursive lock.

In the following recursive lock scenario, lightweight locking for a will be inflated to a heavy monitor, resulting in lower performance compared to stack locking:

```
synchronized (a) {      // monitor_enter a
  synchronized (b) {    // monitor_enter b
    synchronized (a) {  // monitor_enter a
      ...
    }                   // monitor_exit  a
  }                     // monitor_enit  b
}                       // monitor_exit  a
```

In addition to weaker recursive lock optimization, lightweight locking has two main limitations related to JIT compilation:

1. Unlocking must follow the locking order.
The new lightweight lock requires that unlock operations must be executed in the reverse order as the corresponding lock operations, following a "last-in, first-out" stack principle, i.e., the JIT compiler cannot generate the following unlock sequence:

```
monitor_enter a
  monitor_enter b
  ...
  monitor_exit a
monitor_exit b
```

With stack locking, as long as there are no intervening operations between unlocks, the unlock order does not affect program correctness. However, with lightweight locking, because locking and unlocking are push and pop operations on a lock stack, incorrect unlock order leads to incorrect states: a Java object in the lock stack is with mark word showing unlocked; a Java object outside of the lock stack is with mark word showing lightweight locked. Thus, with lightweight locking, unlock operations must strictly follow the LIFO order.If the unlock order is incorrect, it will result in logical errors in the program.

2. Lock elimination based on escape analysis is more complex.
Consider the following code:

```
obj = new Obj
synchronized (obj） {  // moniter_exter obj
  ...                  // may trigger deoptimization
}                      // monitor_exit  obj
```

Assume that obj does not escape. In theory, JIT compiler can eliminate both the object allocation and the lock/unlock operations entirely. However, in the case of deoptimization, the handling differs between stack locking and lightweight locking: with stack locking, the JVM can reallocate the object during deoptimization and simply acquire the stack lock for it. With lightweight locking, after reallocating the object, the JVM cannot directly acquire the lightweight lock. Instead, it must check if the lock is at the top of the lock stack. If other Java objects have already been locked in the synchronized block, the new object’s lock cannot be placed at the top of the stack. Doing so would cause the same issues as aforementioned out-of-order unlocking. To avoid errors, the safest approach is to inflate the new object’s lock to a heavy monitor.

To summarize, As a replacement for the legacy stack locking, lightweight locking offers the primary advantage of removing the reference to the Java stack frame from the object header, thereby simplifying the object header structure. However, it also introduces several significant limitations:

1. Limited numbers of lightweight locks. Each thread can hold up to 8 lightweight locks. Modifying this limit requires recompiling the JDK.
2. Inefficient recursive lock handling. The lightweight locking is less efficient at handling recursive locks, making it prone to lock inflation.
3. JIT compiler unfriendly. The new lock mechanism imposes strict unlock-order requirements, and also complicates the implementation of lock elimination.

Despite these limitations, complex locking scenarios are rare in most real-world applications. As a result, the impact of these limitations on overall application performance is minimal.

# New Object to ObjectMonitor mapping

To remove the heavy monitor reference from the object header, JDK 24 introduces a global concurrent hash map to map Java objects to heavy monitor [7]. This mechanism is enabled via -XX:+UseObjectMonitorTable.

Although the implementation details of this concurrent hash map are beyond the scope of this discussion, the new mapping method has several notable drawbacks:

1. Increased memory overhead. In the old mechanism, the heavy monitor reference was directly stored in the Java object header, utilizing the object’s own memory space. In the new mechanism, the JVM must maintain an additional pair of references, pointing to the Java object and the heavyweight lock respectively. Additionally, the hash table itself consumes extra memory.
2. Synchronization on inserting/deleting map entries. To ensure that a Java object is always mapped to the same heavy monitor, any insert or delete operations in the global hash map must be thread-safe, requiring synchronization.Yet, this overhead is relatively minor because lock inflation and GC reclaiming of locked objects are both rare events. And secondly, these operations are already time-consuming, so the added synchronization cost is negligible in comparison.
3. Higher cost for monitor lookup. In the old mechanism, retrieving the heavy monitor reference required only one memory access, often to memory that was already cached by the CPU, making it highly efficient. In contrast, the new mechanism requires a lookup in the global hash map, which involves multiple memory accesses. In the worst-case scenario, the JVM may need to traverse the entire hash map to find the target object’s mapping entry. If other threads modify the hash map during the lookup (e.g., by inserting or deleting entries), the current CPU’s cache will be invalidated, further increasing monitor lookup latency.

Because lock lookups are not uncommon during application execution, the additional memory accesses and cache invalidations introduced by the new mapping method can significantly slow down lock acquisition. Furthermore, the complex hash table lookup logic can impact JIT-compiled code: If the JIT compiler inlines the lookup logic into the compiled code, it can increase the size of the generated code, which may negatively affect both performance and memory usage.

To address the monitor lookup issue, the JVM introduces a thread-local cache in the new mapping mechanism: When the JVM first queries the global hash map, it caches the result in thread-local memory. If the same thread later attempts to lock the same Java object, the JVM will first check the thread-local cache and directly return the heavy monitor without querying the global hash map. This reduces the frequency of global hash map lookups and improves locking performance.

The actual data structure is as follows:

```
class OMCache {
  struct OMCacheEntry {
    oop _oop = nullptr;
    ObjectMonitor* _monitor = nullptr;
  } _entries[8];
  const oop _null_sentinel = nullptr;
}
```

The lookup operation can be described using the following pseudo-code:

```
def get_monitor(obj):
  int i = 0
  while _entries[i]._oop != null:
    if _entries[i]._oop == obj:
      return _entries[i]._monitor
    else: i++
  call slow_path_lookup
```

The JIT compiler inlines the above lookup logic into the compiled code as a fast path to improve monitor query efficiency. If the thread-local cache does not contain the corresponding mapping, the compiled code falls back to a more expensive JNI call into HotSpot, where the global hash map lookup is performed, and the thread-local cache is refilled.

However, there is a critical issue in this thread-local caching mechanism in the presence of GC. We know that Java object references stored in the thread space are treated as GC roots, meaning that the GC will automatically mark those objects as alive. Furthermore, the GC will mark all objects directly or indirectly referenced by those cached objects, preventing them from being collected. This can result in unnecessary retention of objects, leading to increased memory usage and delayed reclamation of otherwise garbage-eligible objects.

To mitigate this issue, the JVM clears the thread-local mapping cache at every triggered safe point. This prevents unnecessary object retention, ensuring that objects not actively used by the application are properly reclaimed by the GC. However, this introduces another performance penalty: after the cache is cleared, if the program needs to lock the same Java object again, the compiled code must call into HotSpot via JNI to re-perform the global hash map lookup and refill the cache.

In summary, the new mapping mechanism for heavy monitor removes the reference from the Java object header at a significant lookup cost. This performance degradation is one of the key bottlenecks preventing Lilliput from being fully adopted in production.

# Lilliput 1

JDK 24 has integrated Lilliput's implementation [8], which is activated by via -XX:+UseCompactObjectHeaders. This implementation relies on the two locking mechanisms previously mentioned: lightweight locking and the new mapping method for heavy monitors. When Lilliput is enabled, both mechanisms are enforced. Additionally, Lilliput makes the following adjustments to the structure of the mark word:

```
CCCCCCCC CCCCCCCC CCCCCCHH HHHHHHHH HHHHHHHH HHHHHHHH HHHHH--- -AAAASLL
```

The compressed class pointer now occupies only 22 bits, which reduces the number of classes that can be indexed to 2²² = 4,194,304. The subsequent 31 bits are used for the hash code, followed by 4 bits reserved for Project Valhalla, 4 bits for GC age, 1 bit for the self-forwarded flag used by GC, and 2 bits for lock state.

Apart from saving memory overhead in the object header, integrating the class pointer into the mark word affects Java applications in the following ways:

1. Initializing the object header during allocation is reduced from two write operations to a single write operation with a few accompanying arithmetic calculations. Originally, write to object header was as follows:

```
obj._mark     = 0b01                          // memory write
obj._metadata = COMPRESSED_CLASS_POINTER      // memory write
```

When Lilliput is enabled, it is changed to:

```
tmp0          = COMPRESSED_CLASS_POINTER << 42
tmp1          = 0b01 | tmp0
obj._mark     = tmp1                          // memory write
```

For allocation with known class, the COMPRESSED_CLASS_POINTER is a constant. Therefore, in JIT compilation, these calculations are typically constant folded, and the pseudocode can be simplified to:

```
obj._mark     = SHIFTED_CLASS_POINTER_OR_0B01 // memory write
```

2. Reading the Java class is transformed from a single read operation to a read operation followed by several calculation operations. To illustrate this, let's consider the instanceof check for a final class: since a final class has no subclasses, the instanceof check will be optimized to directly read the class pointer and compare it with the target class. Originally, the corresponding pseudocode for this operation is as follows:

```
tmp0          = obj._metadata                 // memory read
isInstance    = tmp0 == COMPRESSED_CLASS_POINTER
```

When Lilliput is enabled, the instanceof check changes to:

```
tmp0          = obj._mark                     // memory read
tmp1          = tmp0 >>> 42
isInstance    = tmp1 == COMPRESSED_CLASS_POINTER
```

which is equivalent to:

```
tmp0          = obj._mark                     // memory read
tmp1          = tmp0 & 0xFFFF_FC00_0000_0000
isInstance    = tmp1 == SHIFTED_CLASS_POINTER
```

This is because, in the former case, the bitwise shift operation in the second line effectively clears the lower bits, avoiding the need for an additional masking operation. Since application code usually performs further operations on the class of the object, the JIT compiler typically prefers the former approach.

3. Reading the cached identity hash code of a Java object requires additional masking operation. Originally, the higher bits of the mark word were unused, and the default value was 0. Therefore, the JIT compiler could omit the masking operation after reading the cached identity hash code. However, when Lilliput is enabled, the lowest bits of the class pointer may no longer be 0. Thus, after reading the cached identity hash code, an additional masking operation must be performed:

```
tmp0          = obj._mark                     // memory read
tmp1          = tmp0 >>> 11
hash          = tmp1 & 0x7FFF_FFFF
```

4. Different array types have different offsets of the first element. In the JVM, array elements need to be aligned according to their type width. For example, arrays of long or double types, as well as Java object arrays with -XX:-UseCompressedOops, must be aligned to 8 bytes. Since array objects require an additional 4 bytes to store the array length, the first element of these arrays starts at the 16-byte position. In contrast, for other types of arrays, the first element starts at the 12-byte position.

It can be seen that Lilliput has both positive and negative impacts on Java applications. While it significantly reduces the size of Java object headers, its prerequisites, particularly the new mapping for heavy monitors, are not friendly for Java applications with lock contention. The designers of Lilliput hope to resolve the performance issues introduced by the new mapping method in JDK 25, otherwise -XX:+UseCompactObjectHeaders will not become the default option. At the same time, they hope to eliminate stack locking in JDK 26, making the lightweight locking the only option.

However, even though Lilliput reduces the size of the Java object header, it does not necessarily reduce the overall size of the Java object. This is because Java objects need to be aligned to 8 bytes. For example, for an empty array object, the original object header occupies 12 bytes, and the array length occupies 4 bytes, making the total size 16 bytes, which is aligned to 8 bytes. When Lilliput is enabled, the object header size becomes 8 bytes, while the array length still occupies 4 bytes. Therefore, an additional 4 bytes of padding is required to align the total size to 8 bytes. As a result, Lilliput does not optimize the memory overhead of empty array objects.

Considering that many core classes in the Java class library have already been optimized for 8-byte alignment, enabling Lilliput is likely to generate Java objects with 4 bytes of padding, making it ineffective at optimizing memory overhead. Next, we will further illustrate this phenomenon.

# Java Object Layout

OpenJDK Code Tools project contains a small tool called jol [9], which can analyze the memory layout of Java objects. For example, for the java.lang.String class, jol can generate the corresponding memory layout based on the user's configuration:

```
$ java -jar jol-cli.jar internals java.lang.String
java.lang.String object internals:
OFF  SZ      TYPE DESCRIPTION               VALUE
  0   8           (object header: mark)     0x0000000000000001 (non-biasable; age: 0)
  8   4           (object header: class)    0x00182b08
 12   4       int String.hash               0
 16   1      byte String.coder              0
 17   1   boolean String.hashIsZero         false
 18   2           (alignment/padding gap)
 20   4    byte[] String.value              []
Instance size: 24 bytes
Space losses: 2 bytes internal + 0 bytes external = 2 bytes total
```

In this output: the first column represents the offset; the second column represents the size (in bytes); the third column shows the field type; the fourth column provides a description of the content; the fifth column gives the specific value.

For example, the row

```
  8   4           (object header: class)    0x00182b08
```

shows that the offset is 8 bytes, the size is 4 bytes, the type is unspecified, and the content is a compressed class pointer, with the value 0x00182b08. The row

```
 20   4    byte[] String.value              []
```

shows that the offset is 20 bytes, the size is 4 bytes, the type is byte[], the content is the field String.value, and the specific value is [] (an empty array). For non-empty strings, the specific value will be a non-empty array. Note that, due to the implementation of jol, it only calls the default constructor of the target class, so it cannot display the actual content of non-empty strings.

From this example, we can see that for an empty string, the JVM needs to create two objects: one is a String object and the other is a byte array object. Each object's header takes up 12 bytes. The total memory used by these two objects is 24 + 16 bytes, meaning that the memory overhead of the object headers accounts for 60%.

When Lilliput is enabled, the object layout of the String object is as follows:

```
$ java -XX:+UnlockExperimentalVMOptions -XX:+UseCompactObjectHeaders \
  -jar jol-cli.jar internals java.lang.String
java.lang.String object internals:
OFF  SZ      TYPE DESCRIPTION               VALUE
  0   8           (object header: mark)     0x0008500000000001 (Lilliput)
  8   4       int String.hash               0
 12   1      byte String.coder              0
 13   1   boolean String.hashIsZero         false
 14   2           (alignment/padding gap)
 16   4    byte[] String.value              []
 20   4           (object alignment gap)
Instance size: 24 bytes
Space losses: 2 bytes internal + 4 bytes external = 6 bytes total
```

We can observe that the object header size of the String object has been reduced to 8 bytes. However, the JVM adds 4 bytes of padding at the end, so the total size of the object remains 24 bytes. Similarly, the object header of the byte array object has also been compressed to 8 bytes, with an additional 4 bytes of padding at the end. Overall, the memory space saved by compressing the object header in Lilliput is offset by the padding required for aligning Java objects.

Of course, we can adjust the design of key classes in the Java class library based on the implementation of Lilliput. By sacrificing the memory overhead when Lilliput is not enabled, we can ensure that the total size of the fields in these classes is a multiple of 8 bytes. Another possible optimization is to further compress the object header size to 4 bytes, which is the planned improvement for Lilliput 2.

# Lilliput 2

First, it is important to clarify that Lilliput 2 is not included in JDK 24. All known information currently comes from the OpenJDK Lilliput project wiki [10].

The goal of Lilliput 2 is to further compress the object header size to 4 bytes. One of the key improvements is compressing the 31-bit local hash code. To achieve this, Lilliput 2 proposes a clever identity hash code retrieval scheme that ensures consistency while saving space if possible. Specifically, Lilliput 2 divides Java objects into three states:

* Identity hash code never computed: For these Java objects, the JVM does not need to allocate extra space to store the local hash code.
* Identity hash code computed, and the object has 4 bytes of padding at the end: In this case, Lilliput 2 stores the local hash code in the padding area at the end of the object.
* Identity hash code computed, and the object does not have 4 bytes of padding at the end: For these objects, Lilliput 2 requires that, as long as the object has not been moved by GC, the same hash value is returned consistently based on the object’s address. If the object is moved by GC, 8 bytes of additional space must be allocated, with 4 bytes used to cache the identity hash code based on the object’s previous memory address. In this case, the object’s state is similar to the second case, and the cached identity hash code can be accessed by reading the last 4 bytes of the object.

Because this identity hash code caching mechanism requires Java objects to be divided into three states, two additional state bits are needed. As a result, the object header layout for Java objects will change as follows:

```
CCCCCCCC CCCCCCCC CCCHH--- -AAAASLL
```

In Lilliput 2, the compressed class pointer size is reduced to 19 bits, which further decreases the number of indexable classes to 2¹⁹=524,288. Immediately following this, two bits are used to represent the hash code state, 4 bits are reserved for Project Valhalla, 4 bits are for the GC age, 1 bit is the self-forwarded flag used by GC, and there are also two bits for lock states.

Since the number of indexable classes is reduced, an additional mechanism is required to handle cases where the number of classes loaded by the Java application exceeds this limit. The solution proposed by Lilliput 2 is that when all 8 upper bits are set to 1, the remaining compressed class pointer is used as an offset. The JVM will use this offset to store the class pointer at the corresponding position in the Java object.

Specifically, during class loading, the JVM will check if there is enough space in the metaspace to store the class. If there is not enough space, the JVM will insert an additional field before the current class fields and after the superclass fields to store the class pointer. The offset of this extra field will be stored in the remaining 11 bits, as shown below:

```
11111111 FIELDOFFSET HH--- -AAAASLL
```

This solution resolves the issue of the insufficient number of indexable classes.

# Summary

The Lilliput 1 implementation in JDK 24 has certain imperfections, especially regarding its dependency on the new lightweight locking and the new mapping mechanism for heavy monitors. The latter has a significant impact on the performance of Java applications that experience severe lock contention. Lilliput 1 requires additional shift computation operations when loading Java object classes, but the performance impact on Java applications is minimal. Due to the JVM's object alignment mechanism, Lilliput 1's optimization effects on existing Java libraries may not be significant. However, this issue is expected to be improved in the upcoming Lilliput 2.

Those interested in experimenting with Lilliput 1 can do so by using the -XX:+UnlockExperimentalVMOptions -XX:+UseCompactObjectHeaders.
